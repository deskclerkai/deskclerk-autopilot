# 员工、坐席与客户归属

> 适用系统：DeskClerk AI Autopilot
> 最后更新：2026-11-09
> 关联文档：[WhatsApp 账号体系与接入](./WhatsApp-账号体系与接入.md)、[公海机制](./公海机制.md)

## 一句话

**客户归谁，只看系统里的"负责人"这一个字段，跟谁的手机、谁的 WhatsApp 号没有关系。**

## 一、员工是什么

- 员工 = **系统账号**（一个登录邮箱 + 密码）。行业里常叫"坐席"，指的是"一个能登录系统处理客户的人头"。
- 员工**不是** WhatsApp 个人号。整个团队共用公司的 WhatsApp 商业号码（可以有好几个），客户都加在公司的号上。
- 所以不存在"这个客户在谁的手机上"。客户在公司的号里，员工只是登录系统去回消息。

这样带来的直接结果：

| 场景 | 会怎样 |
|---|---|
| 销售离职 | 停用他的账号、把客户转给别人，客户和聊天记录都不丢 |
| 加人 / 减人 | 只在系统里加一个员工账号，不影响 WhatsApp 号码 |
| 换手机 | 员工换手机照样登录，客户不受影响 |
| 老板看全貌 | 所有号、所有客户都在一个后台里 |

## 二、客户归属怎么记

数据库里就一个字段：`contacts.owner_id`。

- 有值 → 这条客户归这个员工，别人看不到（老板、主管按数据范围能看到）。
- 空 → 这条客户没有负责人，进**公海**，符合规则的人可以领。

所以公海页里每行的负责人显示"无主"是对的——**公海的定义就是"没有负责人的客户"**。

## 三、客户是怎么分到员工头上的

一共四种入口，任何时刻归属只有一个：

| 方式 | 谁来做 | 入口 | 效果 |
|---|---|---|---|
| 自己领 | 销售 | 公海页「领取」 | 归属改成自己，计入当天额度 |
| 主管指派 | 老板 / 主管 | 客户池 → 点开客户 → 「负责人」下拉选人 | 直接改成选中的员工 |
| 会话分配 | 老板 / 主管 | 会话台 → 右上「分配给…」 | 这条会话和它的客户一起归给该员工 |
| 离职转移 | 老板 | 设置 → 团队与权限 → 转移 | 名下客户批量转给别人 |

另外两种是"离开"：

- 销售主动「放回公海」→ 归属清空，进入保护期（默认 24 小时别人不能领）。
- 超期未联系（默认 90 天）→ 系统自动回收进公海。

**老板/主管指派时，系统同时改两处**：客户的负责人、以及这个客户的所有会话负责人。否则会出现"客户归 A、会话归 B"的错位。

## 四、团队页每个员工显示什么

| 列 | 含义 |
|---|---|
| 销售 | 员工姓名 + **系统登录邮箱**（不是手机号） |
| 角色 | 老板 / 主管 / 销售 |
| 数据范围 | 老板＝全部客户；主管＝本组；销售＝只有自己名下 |
| 可领标签 | 公海领取范围（设置 → 公海规则 → 领取范围）；不受限显示"不限" |
| 进行中 | 他名下还没结束的会话数 |
| 未读 | 他名下会话里的未读消息数 |
| 负责客户 | `owner_id` 指向他的客户数 |
| 成交 | 他名下已成交的客户数（人工标记） |

点任意一行 → 跳到客户池，按这个员工筛选。

**为什么不显示员工手机号**：客户不在员工手机上，显示了反而让人误以为"客户在这个号上"；同时手机号属于个人信息，没必要出现在团队看板上。

## 四点五、成员从哪来（不会自动同步）

**员工账号是本系统自己建的，不会从 WhatsApp 同步。**

- WhatsApp / Meta 那边只有"商业账户里的管理员/操作员"，那是管广告和号码的人，不是你的销售名单；Cloud API 也不提供"员工列表"接口。
- 所以在 设置 → 团队与权限 → **添加成员** 里填：姓名、登录邮箱、初始密码、角色。创建后员工拿这个邮箱和密码登录。
- 团队表里的「负责客户」数来自本系统的 `contacts.owner_id`，也不是 WhatsApp 给的数据。
- 演示库里预置了 4 个账号（owner / manager / agent / chen），正式上线前请在同一个页面停用或删除它们，再建真实的成员。

## 五、权限矩阵

| 角色 | 能看到哪些客户 | 能看哪些会话 | 能回复消息 | 能做指派 | 能看成交金额 |
|---|---|---|---|---|---|
| 老板 owner | 全部 | 全部号码 | ✅ | ✅ 所有人 | ✅ |
| 主管 manager | 本组 | 本组号码 | ✅（除非设为只读） | ✅ 本组成员 | ✅ |
| 销售 agent | 只有自己名下（公海除外） | 本组号码 | ✅（除非设为只读） | ❌（只能领） | ❌ |
| **只读账号** | 同其角色 | 同其角色 | ❌ | 同其角色 | 同其角色 |

**只读账号**不是第四种角色，而是一个开关：在 设置 → 团队与权限 里点某人的「可回复 / 只读」标签即可切换。
- 适用于：老板助理、财务、运营看数据，但不该直接给客户发消息。
- 只读账号能看会话、客户、看板，输入框会变成"只读账号"提示；调发送接口返回 `403 read_only`。
- 演示库里的 `finance@demo.com` 就是只读账号（售后组，能看 Support 的会话，不能回）。

注：公海对所有角色可见——**无主的客户本来就是公共资源**，只是能不能领由公海规则决定。

## 六、常见误解

| 误解 | 事实 |
|---|---|
| "客户是销售自己加的好友，公司拿不走" | 前提是号码归公司。若销售用私人号加客户，客户就真的在他手上，系统也管不了 |
| "换个人负责，客户要在 WhatsApp 上重新加一次" | 不用。客户加的是公司的号，换的只是系统里的负责人 |
| "会话分给别人了，客户还是我的" | 不是。会话分配会同时改客户负责人，两者始终一致 |
| "公海里看不到负责人是 bug" | 不是。公海 = 无主客户，本来就没有负责人 |

## 七、接口

| 接口 | 作用 | 权限 |
|---|---|---|
| `GET /api/users` | 员工列表（带负责客户数） | 登录即可 |
| `GET /api/team` | 团队看板数据（含领取范围） | 老板 / 主管 |
| `POST /api/contacts/{id}/assign` | `{"user_id": 3}` 指派；`{"user_id": null}` 放回公海 | 老板 / 主管 |
| `POST /api/conversations/{id}/assign` | `{"owner_id": 3}` 分配会话，同时改客户负责人 | 老板 / 主管 |
| `POST /api/users` | 添加成员 `{name,email,password,role,can_reply}` | 老板 |
| `POST /api/users/{id}/reply` | 设 `{can_reply: true/false}`（只读开关） | 老板 |
| `POST /api/users/{id}/transfer` | 把某员工名下客户批量转给别人 | 老板 / 主管 |
| `POST /api/contacts/{id}/claim` | 销售自己领 | 登录即可（受公海规则约束） |

`assign` 会写操作日志（`assign` / `unassign` / `assign_conv`），可在 设置 → 操作日志 查到。

## 八、分配完之后，在哪里回复？

先把两件事分开：

| | 客户归谁跟 | 消息从哪收发 |
|---|---|---|
| 存在哪 | 我们系统的 `owner_id` | WhatsApp 的号码 |
| 谁改 | 老板 / 主管 / 销售自己领 | Meta 的接入方式决定 |
| 客户能感知吗 | **完全不能** | 客户始终对着同一个公司号码说话 |

**分配客户不会改动 WhatsApp 里任何东西**：客户还是发给同一个公司号，只是我们后台记了一笔"这条归谁跟"。

回复在哪做，取决于号码是怎么接进来的，一共三种：

### 方式 A：只用 WhatsApp Business App（手机 App）
- 员工在手机 App 里回。客户收到的还是公司号。
- 我们系统**收不到消息**，也就不能当客服台用（只能当客户档案本）。
- 适合：小团队、不需要多人协作和统计。

### 方式 B：接 Cloud API（本系统的设计模式）
- 消息进到我们系统，员工**在我们后台回复**，系统通过云接口用公司号发出去。
- 这种模式下，**同一个号码不能再用手机上的 WhatsApp Business App 登录**，两边不能同时回。
- 好处：多人共享收件箱、分配、统计、模板、退订管理全部成立。

### 方式 C：Coexistence（App 和 API 共存）
- Meta 近两年提供的模式：同一个号码既能在 Business App 里回，也能接 API，消息双向同步。
- 前提：App 版本 2.24.17+；**每 14 天必须打开一次 App**，否则连接会断；接入后 24 小时内要完成历史同步。
- 限制：群聊不同步、广播列表停用、不能编辑/撤回消息、通话/目录/状态等 API 不支持；App 和 API 共享 20 条/秒的发送速度。
- 我们系统**目前没有做共存接入**，做的（以及规划的）是方式 B。

### 现在这个版本是什么状态

**沙盒**：员工可以在我们系统里点发送，消息只入库、不真的发到 WhatsApp。等拿到 Meta 的 WABA 与 token、填进「号码管理」并完成接口对接后，才会变成真实发送。

一句话：**分配在我们这儿，回复也在我们这儿（方式 B）；想让员工继续用手机 App 回，就得选方式 C，那是另一套接入。**

## 九、手机端怎么用、谁能登 WhatsApp

### 我们的系统：手机浏览器直接打开（H5）

- 员工用手机 Chrome / Safari 打开系统地址就能登录，**不需要装 App**。
- 已做窄屏适配：列表在上、详情在下；左侧导航收成图标；表格可横向滑动。
- 建议员工"添加到主屏幕"，用起来接近 App。以后要做原生 App 或 PWA 可以再单独立项。
- 手机上适合：会话台回复、看客户、领公海、看分层；设置和复杂看板建议用电脑。

### 我们系统的账号 ≠ WhatsApp 账号

| | 我们的系统账号 | WhatsApp 账号 |
|---|---|---|
| 是什么 | 邮箱 + 密码，一个人一个 | 手机号 + 一台设备，一个号一个总收件箱 |
| 谁能登录 | 每个员工都能 | 只有拿着那台手机的人 |
| 有没有"员工账号" | 有 | **没有** |

**员工不能、也不需要登录 WhatsApp。** 他们在我们系统里工作；WhatsApp 里没有"哪个员工处理哪条聊天"这个概念。

### 三种接入下，谁能用 WhatsApp 官方手机 App

| 接入方式 | 员工 | 老板 / 主管 | 谁能看到这个号的全部聊天 |
|---|---|---|---|
| **B. 只接 Cloud API**（本系统默认） | 系统 H5 | 系统 H5 | 老板（系统权限决定） |
| **C. 共存（App + API）** | 系统 H5 | 系统 H5 + 手机 App | **拿到手机的人** |
| A. 只用 Business App | 系统收不到消息 | 手机 App | 手机持有人 |

关键点：

- **B 模式下这个号不能登录任何手机 App**，老板也不行，所有人在系统里操作。
- **C 模式下"老板/主管能看到全部"不是权限，是设备**：谁拿到那台装了 WhatsApp Business 的手机，谁就看到全部聊天。WhatsApp 不认我们的角色，也不支持按人分。
- 所以共存时手机只发给老板/主管，建议只当"随身查看器"；一线销售不装。

### 一句话回答

- 员工手机上**能用我们的系统**（浏览器打开，已适配）。
- 员工**不能登录 WhatsApp 官方 App**，也不需要。
- 只有老板/主管在 WhatsApp 里看全部——前提是走共存，并且手机只在他们的设备上。
